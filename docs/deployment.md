# Deployment Guide: Render (Django + Flask) and Vercel (React)

Three services, all on free plans:

| Service | Host | What it is |
|---|---|---|
| `truck-risk-engine` | Render web service | Flask: weather, risk rules, heatmap frames (internal, token-protected) |
| `truck-routing-api` | Render web service | Django: the only public API (`/api/*`) |
| Frontend | Vercel | Static React build that calls the Django API |

Render setup comes from `render.yaml` at the repo root. Python is pinned by `.python-version` (3.14).

> **Never commit secrets.** Every key below is entered in the Render or Vercel dashboard only.

---

## Live deployment

| Piece | Where | URL |
|---|---|---|
| Frontend + Open-Meteo relay | Vercel project `truck-flow` (root `frontend`) | https://truck-flow-psi.vercel.app |
| Django API | Render `truck-routing-api-qtf7` (Oregon, Blueprint) | https://truck-routing-api-qtf7.onrender.com |
| Postgres | Render `truck-routing-db-qtf7` (Oregon, Blueprint) | internal |
| Flask risk engine | Render `truck-risk-engine-ohio` (Ohio, created by hand) | https://truck-risk-engine-ohio.onrender.com |

The Blueprint added a `-qtf7` suffix to every name. The live setup differs from `render.yaml` in two ways:

- **The risk engine runs in Ohio, outside the Blueprint.** It was recreated there while diagnosing the Open-Meteo limit (see "Open-Meteo relay" below). The Blueprint's own risk engine, `truck-risk-engine-qtf7` in Oregon, is unused. Deleting it while the Blueprint is connected makes Render recreate it on the next sync, so disconnect the Blueprint first (or remove the service from `render.yaml`).
- **`OPEN_METEO_URL`** is set on the Ohio risk engine to `https://truck-flow-psi.vercel.app/api/open-meteo`. It is not in `render.yaml`.

Both live core checks (§5) passed against the live API on 2026-11-21.

## 0. Before you start

1. Push `main` to GitHub (already done for this repo).
2. Pick the shared internal token and keep it somewhere safe. Generate one locally:

   ```powershell
   python -c "import secrets; print(secrets.token_urlsafe(32))"
   ```

   You will paste this **same** value into both Render services.
3. Have your HERE API key ready.

## 1. Deploy both Render services from the Blueprint

1. Render dashboard → **New** → **Blueprint** → connect the GitHub repo → select `main`.
2. Render reads `render.yaml` and shows two services and one Postgres database (`truck-routing-db`). `DATABASE_URL` is wired to the database automatically, and Django applies migrations each time it starts. Render's free Postgres is time-limited: check Render's current terms and upgrade or export before it expires. It asks for every variable marked `sync: false`. Fill in what you can now:

   | Service | Variable | Value |
   |---|---|---|
   | truck-risk-engine | `RISK_ENGINE_TOKEN` | the token from step 0 |
   | truck-risk-engine | `NWS_USER_AGENT` | `truck-routing (contact: you@example.com)`; sent to NWS with every weather-alert request |
   | truck-routing-api | `HERE_API_KEY` | your HERE key |
   | truck-routing-api | `RISK_ENGINE_TOKEN` | **the same** token |
   | truck-routing-api | `RISK_ENGINE_URL` | leave a placeholder for now, e.g. `https://example.com` |
   | truck-routing-api | `ALLOWED_HOSTS` | leave a placeholder, e.g. `localhost` |
   | truck-routing-api | `CORS_ALLOWED_ORIGINS` | leave a placeholder, e.g. `http://localhost:5173` |

   `DJANGO_SECRET_KEY` is generated by Render. `DJANGO_DEBUG=false` and `TRUCK_TARE_LB=35000` are set by the Blueprint.
3. Click **Apply**. Both services build. Note their URLs, for example:
   - `https://truck-risk-engine.onrender.com`
   - `https://truck-routing-api.onrender.com`

## 2. Point Django at Flask and at its own host

In **truck-routing-api → Environment**, set:

| Variable | Value |
|---|---|
| `RISK_ENGINE_URL` | `https://truck-risk-engine.onrender.com` (no trailing slash) |
| `ALLOWED_HOSTS` | `truck-routing-api.onrender.com` (host only, no `https://`) |

Save; Render redeploys. Check it:

```powershell
curl.exe https://truck-routing-api.onrender.com/api/health
```

Expected: `{"status":"ok","risk_engine":"ok",...}`. If `risk_engine` is `"down"`, the risk engine is still waking up (free services sleep after 15 min idle and take about a minute to wake). Retry after a minute; if it stays down, check that `RISK_ENGINE_URL` and both `RISK_ENGINE_TOKEN` values match.

## 3. Deploy the frontend on Vercel

1. Vercel → **Add New** → **Project** → import the GitHub repo.
2. **Root Directory**: `frontend`. Framework preset: **Vite** (build `npm run build`, output `dist`).
3. Environment variables:

   | Variable | Value |
   |---|---|
   | `VITE_API_BASE_URL` | `https://truck-routing-api.onrender.com` |
   | `VITE_MAP_STYLE_URL` | `https://tiles.openfreemap.org/styles/liberty` |

4. Deploy and note the URL, e.g. `https://truck-routing.vercel.app`.

## 4. Allow the frontend origin (CORS)

In **truck-routing-api → Environment** set `CORS_ALLOWED_ORIGINS` to the Vercel URL, e.g. `https://truck-routing.vercel.app` (exact origin, no trailing slash; comma-separate several). Save and let it redeploy.

Vercel preview deployments get different URLs. Add one to `CORS_ALLOWED_ORIGINS` if you want to test a preview.

## 5. Check the live site (core checks)

1. Open the Vercel URL. The header pill should go from **Waking services…** to **Services ready**. On a cold start this can take about a minute; use **Retry** if it shows "Risk engine down".
2. Run a trip (e.g. Denver, CO → Salt Lake City, UT, Mountain time). Check that you see 3 routes, every checkpoint with risk and ETA, the route cards with the recommendation (CORE-5), and the heatmap over the corridor with a 0–48 h slider (CORE-6).
3. From your machine, run the scripted checks against the live API:

   ```powershell
   cd backend
   python scripts/core_check_chunk2.py --base https://truck-routing-api.onrender.com
   python scripts/core_check_chunk4.py --base https://truck-routing-api.onrender.com
   ```

## Notes and limits

- **Cold starts:** both Render services sleep after 15 minutes without traffic. The frontend calls `/api/health` on load to wake them before the first submit.
- **Caches are in memory**, one worker per service, so a redeploy or restart empties them. That only costs a little extra time on the next request.
- **Open-Meteo free tier:** a heatmap requests up to 256 locations (cached for 30 min per corridor). That is fine for a demo, but heavy use can reach the free daily limit.
- **Logs never contain the HERE key:** httpx request logging is kept at WARNING (`backend/config/settings.py`).

## Keeping the services awake

Free Render services sleep after 15 minutes without traffic, and the first request after that waits about a minute. `.github/workflows/keep-awake.yml` calls `/api/health` every 10 minutes (the health check also pings the risk engine, so one call wakes both). Run it only while someone is reviewing the app: Render's free plan gives 750 instance hours per workspace per month, and two services awake all month need about 1,488. Turn it off afterwards:

```powershell
gh workflow disable keep-awake.yml
```

`gh workflow enable keep-awake.yml` turns it back on; **Run workflow** on the Actions tab pings once by hand.

## Open-Meteo relay

Open-Meteo's free tier limits calls per outbound IP. Render's free services share outbound IPs that other tenants use up, so the risk engine gets `429 Daily API request limit exceeded` before making any real use (seen in both Oregon and Ohio). The frontend project therefore ships a small Vercel Function, `frontend/api/open-meteo.ts`, that forwards forecast requests to `https://api.open-meteo.com/v1/forecast` from Vercel's network. Its upstream is fixed, so it is not an open proxy.

Point the risk engine at it in **truck-risk-engine → Environment**:

| Variable | Value |
|---|---|
| `OPEN_METEO_URL` | `https://<your-vercel-app>.vercel.app/api/open-meteo` |

Unset, the risk engine calls Open-Meteo directly (local development and tests).

## Accounts and the database

- **Staff account** (sees `/api/admin/stats`: users by country and continent): open **truck-routing-api → Shell** and run `cd backend && python manage.py createsuperuser`. It asks for email, name, country code (e.g. `US`) and password.
- **Rate limits by client IP** need the real client address. `NUM_PROXIES=1` (render.yaml) takes the last address that Render's proxy appended to `X-Forwarded-For`. Check it once after deploy: sign-in attempts from two different networks (e.g. phone data and Wi-Fi) should each get their own 10/min allowance. If every visitor shares one counter, adjust `NUM_PROXIES` (2 if there is a second proxy hop) and redeploy.
- **Locally** no setup is needed: without `DATABASE_URL`, Django (with `DJANGO_DEBUG=true`) uses `backend/db.sqlite3` (git-ignored). Run `python manage.py migrate` from `backend/` once.
